# Work → Codex 개발 규칙
Work는 요구 동작·범위·완료 조건을 결정하고, Codex는 기존 코드에 맞춰 구현·검증한다. Work가 결정한 요구사항을 재설계하거나 구현 세부사항을 양쪽에서 중복 분석하지 않는다.
게임 규칙·공개 통신·저장 의미·의존성 정책·범위 변경이 필요하면 충돌 위치와 대안을 제시한다.

## 최소 Context
현재 요청 → README의 관련 문서 → 파일/심볼 검색 → 관련 절·코드 순으로 좁게 읽는다.
독립 조회는 묶고, 변하지 않은 파일·검색·성공한 검증을 반복하지 않는다. 근거가 충분하면 탐색·분석·검증을 종료한다.
내부 근거로 해결되는 문제는 웹을 사용하지 않는다. 현재성이 필요한 외부 사실만 공식 근거로 확인한다.
단일 에이전트가 기본이다. 독립적인 큰 작업에서만 중복 Context보다 이점이 큰 위임을 고려한다.

## 작업 크기와 인계
- Small: 요청에 목표·변경·완료 조건만 작성. 별도 Spec 없음.
- Medium: 목표·범위·요구 동작·제약·Acceptance Criteria만 전달.
- Large: 짧은 Active Spec 작성. 데이터·통신·저장·오류·시험 등 실제 영향 있는 항목만 추가.
빈 항목·대화 전문·프로젝트 규칙·전체 기획을 반복 전달하지 않는다.
Active Spec 경로는 PROGRESS 한 곳에서 관리한다. 구현 대상 경로, 필요한 설계 절과 문서 전달본을 명시한다.
Work와 Codex의 자동 동기화를 가정하지 않는다. 구현 저장소가 확정되면 그 docs를 공동 기준으로 사용하고, 사본은 기준 경로·리비전 또는 전달 시각으로 식별한다.

## 검증 예산
- Low: 문서 링크·변경 내용 또는 직접 관련 동작의 최소 확인.
- Medium: 관련 테스트와 호출부·연동 영향 확인.
- High: 저장·재화·소유권·통신·복구 변경에 필요한 경계·실패·중복 요청·통합·회귀 확인.
가장 작은 의미 있는 검증부터 실행한다. 통과 후 새 위험 근거가 없으면 확대하지 않는다.
변경을 묶어 빌드하고, 같은 코드 상태에서 성공한 빌드·테스트는 반복하지 않는다.
실행하지 못한 필수 검증은 이유와 남은 위험을 기록한다. 미실행을 통과로 보고하지 않는다.

## 보고·문서 Sync
완료 보고는 변경·검증·미해결 사항만 짧게 작성한다. 전체 코드·기록·배경은 재출력하지 않는다.
실제 수정 후 PROGRESS를 현재 상태·Active Spec·다음 작업 위주로 갱신한다. 테스트 실행 시 TEST_RESULT에 시각·항목·결과·실패 원인·조치를 기록한다.
별도 Phase 구현·검토 보고서는 복잡한 차이나 독립 증적이 필요한 경우만 작성한다. 그 외 PROGRESS와 TEST_RESULT를 참조한다.
Work는 관련 코드·차이·시험 증거로 완료 조건을 검토한다. 접근하지 못한 코드를 검토했다고 표현하지 않는다.
버그 수정은 장기 설계 갱신이 보통 불필요하다. 동작·구조 변경은 담당 설계만 갱신한다.
완료 Spec은 필요한 최종 결정·이유를 담당 설계에 반영한 뒤 archive로 분리하고 Active 링크를 제거한다.
규칙 개선은 반복 낭비가 확인될 때 기존 규칙을 통합·교체한다.

## 첫 Phase
최소 개발 환경·서버와 클라이언트 연결을 우선한다. 버전 조합·구조·입력·화면·요청/응답·완료 조건을 먼저 확정한다.
클라이언트·전용 서버 기동과 연결을 검증한 뒤 캐릭터·저장으로 진행한다. 시험 운영 전체를 한 번에 구현하지 않는다.
